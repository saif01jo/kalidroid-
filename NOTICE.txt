WHY "START VM" CLOSED THE APP  (all three fixed in 1.2.9-kalidroid.5 and later)
-----------------------------------------------------------------------------
Symptom: the app closed instantly on Start VM. Its diagnostic showed
State: Idle, Boot stage: none, Storage img: not created, no console.log and
no qemu stderr -- i.e. the process died before the VM existed.

1. foregroundServiceType was lost by apktool.
   Original: android:foregroundServiceType = 0x40000000 ("specialUse", API 34)
   Rebuilt : 0x00000000 (apktool 2.7 decodes with an API-33 framework and
             writes an empty value back). On Android 14+ startForeground()
             with no declared type throws MissingForegroundServiceTypeException.
   Fix: patch_fgs.py rewrites the compiled binary AXML after `apktool b` and
   restores 0x40000000. Verify with:
     aapt2 dump xmltree --file AndroidManifest.xml KaliDroid.apk | grep -A3 'E: service'

2. Renaming the broadcast action strings broke R8's hashCode() switches.
   R8 compiles `when (action) { "com.excp.podroid.action.START" -> ... }` into
   a switch on String.hashCode() with the hash baked in as an integer:
       com.excp.podroid.action.START = 0x48aa4b9c
       com.excp.podroid.action.STOP  = 0x8ebb2d68
   The rename (kalidroid1..5) changed the literals but not those constants, so
   every branch missed: PodroidService.onStartCommand() returned WITHOUT calling
   startForeground(), and ~10 s later Android killed the process with
       android.app.RemoteServiceException$ForegroundServiceDidNotStartInTimeException
   Same for STOP and for VmControlReceiver's START_VM/STOP_VM switch (and the
   USB permission switch in mh2).
   Fix: the action strings are internal identifiers and are NOT rebranded --
   they stay exactly as upstream. Do not rename them in future builds.

3. The three big assets were stored compressed by apktool.
   PodroidApplication.d() calls AssetManager.openFd() to learn the asset length
   and to skip extraction when files/<asset> already has that length. openFd()
   only works on STORED assets; with compressed assets it fails, the expected
   length is unknown (-1), and the app therefore re-extracted the 450 MB rootfs
   on EVERY app launch.
   Fix: apktool.yml doNotCompress now contains squashfs, img and
   assets/vmlinuz-virt, so those assets are STORED. Extraction runs once.

Guest system (Kali rootfs) -- rebranded in 1.2.9-kalidroid.7
-----------------------------------------------------------
The Alpine->Kali conversion lives in assets/kali-rootfs.squashfs, a 450 MB
squashfs image. Version .7 edits four files inside it:

  /etc/issue      "Welcome to KaliDroid (\\S)" and
                  "Default login:  root  /  kalidroid"
                  (\\S is os-release PRETTY_NAME -> "Kali GNU/Linux Rolling";
                   \\r kernel, \\m arch, \\l tty are unchanged)
  /etc/hostname   podroid -> kalidroid
  /etc/hosts      127.0.0.1 localhost kalidroid
  /etc/shadow     root's sha512-crypt hash replaced with the hash of
                  "kalidroid" (same salt as before, so only the digest differs)

Everything else keeps upstream names, because they are a hard contract with the
app: /usr/local/bin/podroid-getty, podroid-login, podroid-backup, podroid-hostd,
the podroid-*.service units, /var/backups/podroid, /etc/podroid/* and
/mnt/downloads/Podroid/backups. The getty unit prints the banner via agetty -f
/etc/issue; the hostname is applied by /usr/local/lib/podroid/bootstrap.sh.

Rebuild steps (no root needed, but see the permission note):

  unsquashfs -d rootfs assets/kali-rootfs.squashfs
  # edit the four files above
  mksquashfs rootfs kali-rootfs.squashfs.new -comp zstd \
      -Xcompression-level 19 -b 131072 -all-root -noappend -processors 4

Two pitfalls, both hit while making this build:

  a) unsquashfs run as an unprivileged user applies the process umask and
     silently drops setuid/setgid and group/other permission bits. On this
     image that damaged 19,043 files and 2,419 directories (sudo, passwd, su,
     mount and dbus-daemon-launch-helper lost their setuid bit; /etc/shadow
     stayed 0640). fakeroot was unavailable on the build host (no SYSV IPC),
     so the modes were restored by chmod from the pristine `unsquashfs -ll`
     listing of the original image: 19 setuid/setgid files, 0 mismatches left.
     When parsing that listing by hand, the ls-style bits need explicit
     handling: 's'/'t' also imply execute and 'T' is sticky-without-execute.
     A first pass that only looked for 'x' turned /tmp and friends into 1776
     and left them writable-but-not-enterable for other users.
     Always diff `unsquashfs -ll old` against `unsquashfs -ll new` before
     shipping, or a guest built this way will have a broken sudo.
  b) The app decides whether to re-extract by comparing the asset's byte length
     with the extracted file (see fix 3). A rebuilt image that happens to have
     the same length would be ignored. The new squashfs is therefore padded
     with zero bytes to a different length; squashfs readers ignore anything
     after the end of the filesystem.

Launcher icon  (green padlock, 1.2.9-kalidroid.8)
-------------------------------------------------
A glossy green padlock on a dark navy tile, so the icon says what the app is
(a self-contained, locked-away Kali system) instead of borrowing the Kali
dragon mark:

  tile       vertical gradient #0d1220 -> #030409, green bloom (#00c873)
             behind the lock, vignette, thin green rim light
  lock       metallic shackle (gradient #afffd7 -> #007846), body gradient
             #96ffc4 -> #00914e with a bevel, specular sweep, dark keyhole
             (#03160e), soft green halo and drop shadow

  generator  gen_icon.py  (Pillow; no external assets)
  master     gen_icon.py res --master icon/kalidroid-icon-4096.png
             -> 4096x4096 RGBA, full-bleed square (app stores expect a square)
  preview    gen_icon.py res --preview <dir>

It writes four files per density: ic_launcher.png (legacy rounded tile),
ic_launcher_round.png (legacy circle), ic_launcher_foreground.png (adaptive
layer, full-bleed tile with the lock drawn at 72/108 so it reads the same size
once the launcher masks it to the 72dp circle) and ic_launcher_monochrome.png
(themed icons: white lock). res/values/colors.xml ic_launcher_background is
#ff0d1220 to match the tile. Existing resource names and IDs are reused, so the
dex is unaffected. icon/kali-emblem.png is kept for reference but is no longer
used by the generator.

Diagnostic instrumentation (debug only -- not in this release)
-------------------------------------------------------------
smali/org/kalidroid/diag/CrashLog.smali (in this repository) registers an
uncaught-exception handler at the top of PodroidApplication.onCreate() and
appends startup breadcrumbs plus full stack traces to files/console.log, which
the app's "Export diagnostic log" already includes. It was essential on the
test device because logcat is encrypted there (the device prints "beginning of
(HKS)..." gibberish).

apply4.py installs it; apply6.py removes it again, because console.log is also
the QEMU console log and should not be polluted in a release. To debug a device,
re-apply apply4.py and rebuild. CrashLog.smali is provided at the repository
root for that purpose.

Install note
------------
The signing key is new. If a KaliDroid build signed with a different key is
already installed, Android refuses to update it -- uninstall first.

First start extracts the ~450 MB Kali rootfs once and creates the 32 GB disk
image. Keep the app in the foreground until the console appears; needs ~2 GB
free. Later starts skip the extraction (that is what fix 3 restored).

Upgrading from .6 or earlier: the rootfs asset changed length, so the new guest
image IS extracted again on first start. The old guest's writable overlay lives
on the 32 GB disk image and can keep shadowing changed files (the overlay
copy-up of /etc/issue, /etc/hostname, /etc/hosts happens on first boot). If the
old banner or hostname still appears, delete the VM data from the app's storage
screen (or uninstall and reinstall) to get a fresh overlay.

Rebuild recipe
--------------
  apktool d -f -o work <base.apk>
  python3 apply.py      # package/label/links/version (v1)
  python3 apply2.py     # links + version (its action rename is undone by v5)
  python3 apply3.py     # manifest prep + version (v3)
  python3 apply4.py     # diagnostic crash recorder (v4; also bumps to .4/37)
  python3 apply5.py     # revert action names, store assets (v5)
  python3 apply6.py     # remove diagnostics, icon background, version .6 (v6)
  python3 apply7.py     # SSH hint password, icon colour, version .7 (v7)
  python3 apply8.py     # version .8 (v8); the icon comes from gen_icon.py
  # guest image (see the squashfs section): edit rootfs, mksquashfs, pad,
  # then copy over work/assets/kali-rootfs.squashfs
  python3 gen_icon.py work/res          # launcher icon mipmaps (needs Pillow)
  apktool b -o unsigned.apk work
  python3 patch_fgs.py unsigned.apk patched.apk    # restore 0x40000000
  zipalign -p -f 4 patched.apk aligned.apk
  apksigner sign --ks /home/kali/keys/kalidroid.jks --ks-key-alias kalidroid \
      --ks-pass file:/home/kali/keys/kalidroid.pass \
      --key-pass file:/home/kali/keys/kalidroid.pass \
      --min-sdk-version 26 --out KaliDroid.apk aligned.apk
  # sanity checks
  aapt2 dump xmltree --file AndroidManifest.xml KaliDroid.apk | grep -A3 'E: service'
  unzip -lv KaliDroid.apk | grep -E 'assets/(kali-rootfs|vmlinuz|initrd)'   # must say Stored

apply4.py is part of the chain because apply5.py expects the .4 version bump;
if you do not want the diagnostic hooks in an intermediate build, keep apply4
and let apply6 remove them again.
